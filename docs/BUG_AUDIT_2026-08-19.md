### 버그 2: 코멘트 작성 시 다른 필드 롤백 — 원인 확정
`content_body`가 댓글/키워드/본문/크루 등 모든 필드를 담은 단일 JSON 텍스트 컬럼인데, 댓글 추가 로직이 **모달 오픈 시점에 캐시된 stale한 content_body를 재조회 없이 통째로 덮어쓰는** 구조.

- `src/components/ContentDetailModal.tsx:65-78, 105-138` — 모달 열릴 때 한 번만 fetch, 재조회 없이 스냅샷에 댓글만 append 후 전체 컬럼 update (가장 확실한 원인)
- `src/components/ContentsLayout.tsx:509-542` — 동일 패턴 (React state 기반, 재조회 없음)
- 올바른 패턴 참고: `src/components/FinalSubmitForm.tsx`, `src/components/mobile/MobileSubmitModal.tsx:339-356` — update 직전 content_body 재조회 후 merge

**수정 방향**: 댓글 핸들러 2곳을 "update 직전 재조회 후 merge" 패턴으로 통일. 근본 해결은 `content_body`를 jsonb 컬럼화하여 서버에서 `jsonb_set`으로 부분 업데이트.

### 버그 1: 삭제 시 다른 콘텐츠까지 사라짐 — 원인 미확정, 후보 좁힘
- DB 스키마에 FK/CASCADE 없음 (contents는 user_id도 없는 flat 테이블) → DB cascade는 원인 아님
- 모든 delete 쿼리는 `.eq('id', ...)` 또는 `.in('id', selectedForDelete)` — 넓은 필터(author_name 등)로 삭제하는 코드 없음
- 유력 후보: `src/components/ContentsLayout.tsx:204, 441` 일괄삭제의 `selectedForDelete` 배열 — 여러 개 체크 후 취소 없이 다른 삭제 동작을 트리거하면 stale 배열이 남아있을 가능성 (재현 테스트 필요)
- 감사 로그가 프로젝트 전체에 없어 사후 추적 불가능했음
- 프로젝트 루트의 `restore_secret.py`, `patch_secret.js`, `create_admin.js` 등 임시 스크립트가 수동으로 DB를 건드렸을 가능성도 배제 못 함 (별도 점검 필요)

## 공통 구조적 결함
- `supabase_schema.sql`에서 RLS 비활성화 + 대부분의 delete/update가 서버 액션이 아닌 브라우저 클라이언트에서 직접 호출 → 서버/DB 단 권한 검증 부재
- 소유권 판별이 전부 `author_name.includes(name)` 부분 문자열 매칭 (20곳 이상) — 이름이 겹치면 오작동 가능
- select→update 두 단계 로직에 트랜잭션/동시성 가드 없음 (TOCTOU 경합)

## 2차 탐색 추가 발견 (제출/승인 플로우, 모바일, 알림, 관리자 권한)

### 버그 3: 제출/저장 시 status가 현재 상태 무시하고 강제 리셋
- `ProposalSubmitForm.tsx:347` — `status: isDraft ? 'draft' : 'pending'` 무조건 세팅. admin이 이미 `approved` 이상 진행된 기획안을 열어 사소한 수정 후 저장만 해도 status가 `pending`으로 강제 회귀.
- `FinalSubmitForm.tsx:433-439` — `targetStatus = isDraft ? 'approved' : 'final_submitted'`. 이미 `completed`/`uploaded`(발행 완료)된 완성본을 열어 오타만 고치고 임시저장해도 status가 `approved`로 역행 → 발행된 콘텐츠가 갑자기 "업로드됨" 목록에서 사라지고 완성본 대기 상태로 되돌아감.
- `MobileSubmitModal.tsx:394` — 모바일 수정 플로우도 동일하게 `status: mode==='final' ? 'final_submitted' : 'pending'`로 강제 리셋.
- `content.ts:59-66` (`deleteContent`의 완성본만 삭제하는 분기) — 이전 상태와 무관하게 무조건 `status: 'approved'`로 리셋.
→ 공통 원인: "다음 상태"가 현재 DB 상태를 참조/검증하지 않고 클릭한 버튼에 따라 하드코딩됨. 서버 측 상태 전이(state machine) 검증이 전혀 없음.

### 버그 4: 모바일에서 기획안 재수정 시 댓글/완성본 필드가 통째로 삭제됨

- 데스크톱 `ProposalSubmitForm.tsx:152-173, 331`도 동일한 필드 화이트리스트 패턴으로 완성본 관련 필드를 누락시킬 수 있음.

### 버그 5: 관리자 권한 판별 방식이 파일마다 달라 권한 상승 가능
- 서버 코드(`content.ts`, `notice.ts`, `user.ts`, `layout.tsx`)는 엄격하게 `user.email === 'admin@admin.com'` 또는 `user_metadata.is_admin === true`로 체크.
- 반면 다수의 클라이언트 컴포넌트는 `email.includes('admin')` 부분 문자열 매칭 또는 존재하지 않는 `admin@ymc.com`과 비교: `ContentDetailModal.tsx:58`, `OtherProposalsCarousel.tsx:162`, `ProposalSubmitForm.tsx:192`, `FinalSubmitForm.tsx:191`, `ContentsLayout.tsx:306,411,431,491,1747,2261`.
→ 이메일에 "admin"이 포함되기만 하면(예: `kadmin92@yonsei.ac.kr`) 관리자 UI가 열리고, RLS 비활성화 상태에서 브라우저 클라이언트로 직접 임의 콘텐츠의 status를 변경/승인/반려 가능. 실질적 권한 상승 취약점.

### 버그 6: AdminStatusManager가 전이 유효성/소유권 검증 없이 상태를 임의 변경

### 버그 11: 코멘트 이미지가 Storage가 아닌 content_body 안에 base64로 저장되어 row 비대화
- `ContentsLayout.tsx:698-716` — 이미지(최대 2MB)를 base64 data-URL로 변환해 댓글마다 `content_body` JSON 안에 직접 삽입. 댓글마다 row가 ~2.7MB씩 불어나고, 이미 문서화된 "전체 컬럼 덮어쓰기" 버그와 결합해 매번 더 크고 느린 재직렬화가 발생. 클라이언트 2MB 제한은 devtools로 우회 가능(RLS 비활성화).

### 버그 12: 제출 폼 필수값 검증이 클라이언트 전용
- `ProposalSubmitForm.tsx:297-347` 등 3개 제출 폼 모두 브라우저 Supabase 클라이언트로 직접 insert/update하며, 필수값 검증은 전부 클라이언트 JS. RLS 비활성화 + 서버 검증 부재로 devtools/직접 API 호출 시 title/team/content_type이 빈 값인 row도 삽입 가능 → 목록/필터 컴포넌트가 문자열을 non-empty로 가정해 깨진 카드/필터 오작동 유발.

### 확인 결과 문제 없음 (참고용)
- 3개 제출 폼 모두 `isSubmitting` 플래그로 중복 제출 방지 정상 작동.
- 목록/검색/페이지네이션은 전량 클라이언트 사이드 필터링 (서버 `.ilike()`/`.range()` 없음) — 인젝션 위험은 없으나 role 무관하게 전체 contents 테이블이 클라이언트에 전송됨 (기존 RLS 비활성화 이슈와 동일선상).
- 캘린더 컴포넌트에서 날짜/타임존 버그 발견 안 됨.
- 빈 catch 블록들은 전부 JSON.parse 안전 폴백용이며, 실제 DB write는 모두 error 체크 후 alert 처리됨 — 조용한 실패 패턴 추가 발견 없음.

- 이 키는 RLS 여부와 무관하게 Supabase Auth 자체를 우회하는 완전 관리자 권한 — 저장소가 외부에 공유/push되는 즉시 DB 전체 read/write/delete 및 `is_admin` 자가 부여까지 가능.
- **코드 수정과 별개로 지금 즉시**: Supabase 대시보드에서 service_role 키 재발급 + `.env.local` 갱신 필요. (scratch.js/scratch2.js는 삭제 권장, 필요시 git 히스토리에서도 제거 검토)

### 버그 17 (긴급·보안): `/api/notifications`가 URL 쿼리파라미터 `?admin=true`를 그대로 신뢰
- `src/app/api/notifications/route.ts:8-16` — `isAdmin`을 서버가 재검증(`is_admin` metadata 등) 하지 않고 `url.searchParams.get('admin') === 'true'`로만 판단. 게다가 `if (!user && !isAdmin) return 빈 배열` 조건 때문에 **비인증 상태로 `/api/notifications?admin=true`에 접속하면 그대로 통과**되어 전체 리포터의 최근 30건 콘텐츠(제목/상태/피드백 코멘트/작성자명)가 노출됨. 로그인조차 필요 없음.
- 클라이언트(`NotificationsPopup.tsx:17-26`)도 `sessionStorage`의 `isAdminBypass`나 URL의 `?admin=true`를 그대로 서버에 전달하는 구조라 클라이언트-서버 양쪽 다 자기 자신을 신뢰하는 형태.
- 다른 `?admin=true` 사용처(`layout.tsx`, `notices/page.tsx` 등)는 서버 액션에서 `is_admin` metadata를 별도로 재검증하므로 안전 — **이 라우트만 예외적으로 무방비**.

### 버그 18 (보안 참고): admin 로그인 계정이 짧은 숫자 비밀번호의 진짜 Supabase Auth 계정
- `src/app/login/page.tsx:31-34` — `admin`/`0000` 입력을 `admin@admin.com`/`000000` 실제 Auth 계정으로 매핑. `create_admin.js:31-40`에 이 평문 비밀번호가 그대로 기록되어 있고(버그 16과 함께 노출), 앱 자체에 로그인 시도 rate limiting이 없음(Supabase 기본값에만 의존) — brute-force/credential-stuffing에 취약.

### 버그 19: 스키마 기준 파일(`supabase_schema.sql`)에 `DROP TABLE IF EXISTS public.contents` 포함 — 재실행 시 전체 데이터 파괴
- `supabase_schema.sql:2` — 참고/초기화용으로 보이는 이 파일을 실수로 라이브 Supabase SQL 에디터에 재실행하면 `contents` 테이블 전체(기획안/완성본/프로필 데이터 전부)가 즉시 삭제됨. v3/v4는 이 파일 위에 컬럼만 추가하는 증분 패치라 스키마 파일 간 충돌은 없음(스키마 드리프트는 기존 데이터 손실 버그의 원인이 아님으로 확인).

### 버그 20: 프로필 데이터가 `contents` 테이블에 `PROFILE_${email}` 행으로 얹혀 있어 TOCTOU 경합 및 기존 mass-delete 버그에 함께 노출
- `profile/page.tsx:75-91`, `layout.tsx:57-67` — select-then-insert-or-update 패턴에 DB 레벨 UNIQUE 제약이 없음(schema에 title UNIQUE 없음). 탭 2개를 동시에 열거나 자동 복원 effect와 수동 저장이 겹치면 `PROFILE_${email}` 행이 중복 생성될 수 있고, `.single()` 조회가 깨짐. 또한 이 프로필 행도 `contents` 테이블에 있으므로 기존 문서화된 대량삭제 버그의 영향권 안에 있음.

### 버그 21: 보안 헤더 전무
- `next.config.ts`에 `headers()` 설정이 전혀 없음 — CSP/X-Frame-Options/X-Content-Type-Options/HSTS 모두 부재. 버그 14(stored XSS)와 결합 시 CSP가 없어 주입된 스크립트를 막을 방어선이 하나도 없고, clickjacking 방지도 없음.

### 확인 결과 문제 없음 (참고용)
- 회원가입/비밀번호 재설정 플로우는 표준 Supabase Auth 호출만 사용, 자체 구현 토큰 로직 없어 별도 취약점 없음.
- localStorage에는 토큰이 아닌 표시용 캐시(`team_${email}` 등)만 저장 — 민감정보 노출 없음, 다만 기기 간 프로필 표시가 지연될 수 있는 정도의 경미한 UX 이슈.
- package.json 의존성은 최신 버전대(Next 16.2.2, React 19.2.4) — 눈에 띄는 취약 의존성 없음.

### 버그 22 (긴급·보안): `/dashboard?admin=true`, `/search?admin=true`로 아무나 관리자 화면 접근 가능

- `page.tsx:279-373` — 관리자 상태변경 테이블(`AdminStatusManager`)까지 렌더링되어, 스푸핑된 `isAdmin`만으로 임의 콘텐츠의 제출 상태를 변경 가능.

### 참고 확인 사항 (기존 문서 항목 보강, 새 버그 아님)
- `isAdminBypass` sessionStorage 플래그: 현재 코드에 이를 set하는 곳이 없어 오늘 시점엔 비활성 상태지만, 서버 검증이 없는 순수 클라이언트 값이라 devtools로 누구나 직접 설정 가능 — 근본 원인은 버그 17과 동일, 죽은 코드이므로 제거 권장.
- 알림/피드백 "읽음" 상태(`dismissedFeedbacks`, `read_notices`)가 전부 localStorage 기반 — 서버 기록 없어 기기 간 동기화 안 되고 감사 목적으로 신뢰 불가 (낮은 심각도).
- `MobileTrioModal.tsx:389-393`의 `persist()`도 동일한 content_body 전체 덮어쓰기 경합(버그 2와 동일 계열)을 모바일 채팅 모달에서 재현 — 데스크톱뿐 아니라 모바일에도 이미 존재.
- 대시보드 통계 자체(내 것만 필터링하는 부분)는 이중 카운팅 없음 — 다만 `isMine` 판정도 기존 문서화된 fuzzy substring 매칭을 그대로 사용.
- API 라우트는 기존 4개(upload/crew/deadlines/notifications) 외 추가 라우트 없음. 루트 스크립트에 `scratch.js` 외 추가 하드코딩된 키 없음 확인.

## 추가 탐색 가능 및 필요 영역 (6차까지 미커버)

6회의 탐색으로 삭제/코멘트/제출/모바일/API/인증/XSS/시크릿/로그인/프로필/페이지 레벨 권한까지 폭넓게 훑었으나, 아래 영역은 아직 전용 라운드로 다뤄지지 않았음. 재현 테스트 성격이 강한 항목과 정적 코드 탐색으로 커버 가능한 항목을 구분함.

**정적 탐색으로 추가 확인 가능**
- `ContentsLayout.tsx`(3000줄 이상) 내부의 `useEffect` 의존성 배열 누락, 비함수형 `setState(x+1)` 형태의 경쟁 상태 — 5차에서 지정했으나 6차 에이전트가 시간 예산상 깊게 못 들어감
- Supabase Storage 버킷 자체의 public/private 설정 및 정책(버킷 레벨 RLS/정책은 SQL 파일에 없어 대시보드에서만 확인 가능 — 코드 탐색 한계)
- `vercel.json`/배포 설정, 환경별(`NODE_ENV`) 분기 로직 존재 여부
- 타입스크립트 `any` 남용으로 인한 런타임 타입 불일치 지점 전수 조사
- 알림 발송 트리거 조건(어떤 상태 변경이 어떤 사용자에게 알림을 보내는지) 전체 매핑 — 7번에서 일부만 다룸
- PDF 가이드라인 문서(`89687956-..._가이드라인.pdf`)와 실제 코드 검증 로직 간 불일치 여부

**재현/수동 테스트가 필요 (코드 정적 분석만으로는 확정 불가)**
- 버그 1(대량 삭제)의 정확한 재현 조건 — `selectedForDelete` stale 배열 가설 검증

- 버그 20(프로필 중복 행) — 실제 동시 저장 상황 재현
